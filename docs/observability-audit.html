RuneRating telemetry plan

Audit report

Observability that explains what players compare.

RuneRating should use analytics to measure comparison intent, source reliability, detail-page interest, and cache effectiveness without storing raw provider payloads or creating a second RuneRating history archive.

Priority map

What to measure first

Comparison demand

Capture when users submit two RSNs, which page they land on, whether it came from a recent lookup, and whether data was already fresh. This answers the core question: which comparison workflows deserve optimization.

Page and feature interest

Track navigation among Overview, Skills, XP Timeline, Efficiency, Activity, Quests, Combat Achievements, Bossing, Clues, Minigames, and Collections. Pair this with dwell time and interaction depth.

Rich-data searches

The collection item lookup, quest filters, and combat achievement task lookup are the clearest signals for "what data people find interesting." Log search intent and filter combinations, not every keystroke.

Refresh and cache health

Backend events should show scheduled, cooldown, already scheduled, fresh, failed, rate-limited, and unavailable outcomes by source and category. This is the fastest route to finding provider bottlenecks and cache misses.

Audit findings

Instrument around user intent, not raw data.

This repository already has the right product boundaries: external providers stay in SDKs, Convex stores canonical current snapshots, and the web app renders source-independent comparison models. Analytics should preserve those boundaries. Frontend events explain what users attempted and interacted with; backend events explain cache, source, and query outcomes.

Avoid logging raw provider responses, full snapshot values, or unbounded RSN lists. RSNs are public game names, but they are still high-cardinality identifiers; hash or normalize them consistently when they are needed for deduping funnels.

North-star questions

  • 1. Which comparison pages do users reach after submitting RSNs?
  • 2. Which filters and item lookups are actually used?
  • 3. Where do source states block useful comparisons?
  • 4. How often do actions hit fresh cache versus external providers?
  • 5. Which Convex query/action paths are slow, repeated, or error-prone?

Data shape

Keep properties bounded.

Use buckets

Send 0, 1-5, 6-25, 26+ result buckets instead of exact counts where exactness is not needed.

Hash RSNs

Use a stable one-way hash for player identifiers in analytics. Keep display casing out of product analytics unless explicitly needed for debugging.

Whitelist events

PostHog supports autocapture, but RuneRating should disable or restrict it and emit named events for forms, filters, and navigation.

Sample noisy spans

Capture every refresh outcome, but sample successful high-volume read operations after baselines are established.

Implementation plan

Add analytics in layers.

01

Create a shared event contract

Add a typed analytics package or module with event names, property validators, redaction helpers, RSN hashing, and environment gates.

02

Instrument frontend intent

Capture page views through router subscriptions, compare submissions, refresh clicks, filter changes, search submissions, timeline requests, and share actions.

03

Wrap backend operations

Use a small helper around Convex action/mutation handlers to measure duration and emit result-state events. Keep query logging sampled and low-cardinality.

04

Build dashboards

Start with funnels for compare-to-data-ready, page interest, rich-search usage, refresh outcomes, source error rate, and cache hit ratio.

Backend notes

Convex-specific recommendations

Treat RuneRating as its own product surface.

The single-player /rating flow should log request, ready, unavailable, share, copy, and PNG export actions separately from two-player comparisons. Use tier, formula version, source completeness, and score buckets; avoid sending the full scorecard, pillar details, or prestige stats as raw analytics payloads.

Log from actions where possible.

Convex queries should stay fast and deterministic. Prefer backend analytics from actions and mutations that already represent operational transitions: refresh request, source fetch, cache claim, cache refresh, and failure completion.

Do not persist analytics in Convex first.

Product analytics is high-churn operational data. Send it to the analytics provider directly or through a thin internal action. Do not add a durable analytics table unless there is a concrete application feature that requires it.

Use source/category dimensions.

The useful backend dimensions are source, category, operation kind, duration bucket, cache state, and terminal status. Avoid metric names, item labels, and raw external request URLs unless debugging a narrowly scoped incident.

Governance

Rules for useful, low-risk logging

Never log

  • Raw provider payloads
  • Full canonical snapshots
  • Unbounded arrays of item names
  • Browser input values before submit/search debounce
  • API credentials or provider URLs with tokens

Prefer

  • Stable event names
  • Enum-like dimensions
  • Duration and count buckets
  • Hashed normalized RSNs
  • Source freshness and status summaries

Operational controls

  • Environment-specific API keys
  • Local/dev capture disabled by default
  • Sampling for repeated successful reads
  • Short retention for verbose diagnostics
  • Documented event ownership

Rollout

Suggested first milestone

Start with ten named events, no session replay, no broad autocapture, and one dashboard. That is enough to understand whether users search, compare, refresh, and explore detail pages while keeping the data set explainable.

Provider notes

PostHog's browser SDK supports page and interaction capture, and the Node SDK supports queued, batched server-side capture. For single-page apps, configure pageview handling deliberately instead of relying on page-load-only behavior. If analytics loss from blockers matters, evaluate a managed reverse proxy after the first dashboards prove value.
