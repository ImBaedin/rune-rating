RuneRating / Architecture Proposal Research snapshot: June 2026

Normalize once.
Query by product view.

A proposed ingestion, normalization, and Convex storage system for combining official OSRS hiscores, Wise Old Man, and RuneProfile without leaking source contracts into the web app.

Primary recommendation

Transform responses directly into current canonical snapshots. Each source owns explicit fields, Hiscores wins every overlap, and successful refreshes replace prior values. Store no RuneRating history or raw responses.

01

The core decision

Use two data layers and one ownership policy

Layer A / DTO

Source response

Validated inside its SDK package. Exists only during the action. Never imported by the web app and never stored as the product model.

Layer B / Canonical

Current snapshot

The only persisted product data. Source-independent, current, granular where needed, and transactionally replaced when the hourly refresh cooldown allows an update.

Policy / Ownership

Static source authority

Every canonical field has an owner. Hiscores owns all shared metrics. Other providers may write only canonical data that Hiscores does not provide.

Why not one giant player document?

RuneProfile collection logs and detailed combat tasks can grow significantly; Convex documents are limited to 1 MiB and 8,192 array elements. A large document also makes every small refresh invalidate every subscriber.

Why use both documents and rows?

Small bounded categories such as skills are efficient as snapshot documents. Searchable, granular categories such as collection-log items need indexed rows so a specific item can be found and compared without loading a full collection log.

02

What the sources actually provide

Source Best at Shape and hazards Recommended use
OSRS Hiscores Current skill XP, levels, ranks, activities, clues, and boss kill counts. Positional arrays can shift when Jagex adds metrics. -1 commonly means unranked or unavailable, not a real negative. The response has no reliable source observation timestamp. Baseline current snapshot and account lookup. Version the positional manifest and fail visibly on unexpected field changes.
Wise Old Man Historical snapshots, timelines, gains, EHP/EHB, records, achievements, and name history. Nested keyed metrics with a source createdAt. A player can be absent even when the RSN is valid. Historical endpoints are paginated or range-based. Preferred provider for history and efficiency. Fetch history on demand without persisting it as RuneRating history; treat missing players as notConnected.
RuneProfile Quests, diaries, combat achievements, collection log, skills, and typed activity feed. Granular endpoints plus a large full-profile endpoint. Activity is cursor-paginated. Collection data is nested by tab/page/item. Responses are cached for one minute; anonymous traffic is limited to 30 requests/minute. Fetch category endpoints, not the full profile, during normal refreshes. Slice collection log by tab/page and ingest activities idempotently.
Confirmed identity policy: RuneRating identifies a player only by normalized current RSN. It does not attempt to preserve account continuity across name changes. Provider IDs may be retained only as fetch metadata, never as RuneRating identity.
03

End-to-end data flow

1 / PLAN

Refresh request

Resolve RSN, inspect per-slice freshness, acquire leases, and schedule only missing or stale slices.

→
2 / FETCH

Source action

SDK validates the DTO, maps transport errors, and returns rate-limit and source-time metadata.

→
3 / NORMALIZE

Pure adapter

Convert DTO into a canonical-keyed batch. No database calls, no precedence decisions.

→
4 / COMMIT

Internal mutation

Reject stale runs, replace the owned canonical snapshot rows, and update refresh state.

REACTIVE OUTPUT
Current canonical rows update
ATOMIC REPLACEMENT
Previous source/category snapshot is removed
VISIBLE QUALITY
Source slice state becomes fresh

Refresh by slice, not just by source

A RuneProfile collection page and account summary have different cost and size. Track states such as runeProfile:summary, runeProfile:quests, and runeProfile:collection:Bosses independently, while enforcing the configured player-level refresh cooldown.

Commit by completed slice

Do not wait for all sources before writing. Hiscores can update the comparison immediately while RuneProfile or WOM is unavailable. The UI sees each successful slice through Convex subscriptions.

04

The normalization contract

normalization/types.ts source-independent write command 
type NormalizationBatch = {
  requestId: string;
  playerRef: {
    normalizedRsn: string;
    displayRsn: string;
    sourcePlayerId?: string;
  };
  source: Source;
  slice: SourceSlice;
  fetchedAt: number;
  observedAt: number | null;
  sourceUpdatedAt: number | null;
  schemaVersion: number;
  fingerprint: string;
  replacements: Array<{
    category: Category;
    segment: string;
    metrics: CanonicalMetric[];
    items: CanonicalItem[];
    completeness: "complete" | "partial";
  }>;
  warnings: NormalizationWarning[];
};

Adapters only translate

normalizeHiscores(dto), normalizeWomSnapshot(dto), and normalizeRuneProfileQuests(dto) are pure, fixture-testable functions.

Ownership prevents conflicts

A static ownership map defines which source may write every canonical category and field. Hiscores owns all overlaps; a non-owner value is discarded before the commit mutation.

Unknown is rejected

Unknown metric keys, impossible values, missing expected fields, and source drift fail the affected source/category refresh and are logged. Non-canonical values are never persisted.

RULE 01

Missing is null

Convert source sentinels such as hiscores/WOM -1 into null plus an explicit availability reason. Preserve real zero.

RULE 02

Time has two meanings

Store observedAt from the source when available and always store fetchedAt. Never pretend fetch time is source observation time.

RULE 03

Keys are canonical

Convert names and numeric IDs into versioned keys such as skill.attack.xp and boss.zulrah.kills.

RULE 04

Completeness is explicit

A category reports whether its list is complete, partial, or unavailable. Absence from a partial list cannot mean false or zero.

05

Recommended Convex storage model

IDENTITY
Who is this?

players

Current display RSN, normalized RSN, last requested time, last successful snapshot time, and refreshAllowedAt. The normalized RSN is the identity.

by_normalized_rsn · by_refresh_allowed_at
INGESTION
What arrived?

snapshotStates

Status, source, category, request ID, active revision, last attempt, and last success for the current snapshot.

refreshLeases

One short player-level lease prevents concurrent refresh sessions and protects the hourly cooldown.

runtimeConfig

Database-managed refresh cooldown and source enablement. Initial cooldown: one hour per RSN.

CURRENT SNAPSHOT
What should the UI read?

categorySnapshots

One current, bounded canonical document per player/category/segment. Best for skills, hiscores activities, category summaries, and other fixed-size sets.

by_player_category_and_segment

canonicalItems

Current granular rows for collection items, quests, diary tiers, and combat tasks. Each row carries a canonical key, label, state/quantity, group, source, and snapshot revision.

by_player_category_revision_and_key · by_player_category_revision_and_group
SEARCH
Find one item quickly

canonicalDefinitions

Source-independent catalog of known item/task keys and labels. Its search index finds an item even when neither player owns it.

by_category_and_key · search_label filtered by category

Two-player item lookup

Once catalog search resolves a key, query each player's active-revision row. An absent row means “not owned” only when that player's category snapshot is marked complete.

Document sizing strategy
Embed bounded sets: skills, hiscores activities, clue tiers, and category summaries.
Use indexed rows: current obtained items/tasks, plus completeness metadata to distinguish false from unknown.
Replace by revision: write a new revision, atomically swap activeRevision, then delete the old revision in bounded cleanup batches.
06

Static source ownership

There is no runtime reconciliation layer. Each canonical field has one configured owner. Hiscores owns every shared metric, so a later WOM or RuneProfile refresh cannot overwrite Hiscores values.

Canonical area Owner Write rule
skills, ranks, boss KC, clues Hiscores Always authoritative. Other providers' overlapping values are ignored.
EHP, EHB, gains, records Wise Old Man Write current efficiency summaries. Return provider history on demand without storing it.
quests, diaries, collection log, combat tasks RuneProfile Replace current granular canonical rows; show partial or unconnected explicitly.
provider history and activity Original provider Fetch and transform for the response only. Do not persist in RuneRating.

Ownership map

Keep a typed canonical-key-to-source map in backend policy code and test that every writable key has exactly one owner.

Non-owner values

Discard them during normalization. They are not persisted, compared, or exposed to the web app.

Provenance

Current canonical rows retain only their owner source and fetched timestamp so freshness remains explainable.

Query the product, not the database

Typical comparison query
comparisons.getCategory({
  leftRsn: "player a",
  rightRsn: "player b",
  category: "skills"
})

// Internally:
// 1. Resolve both players by normalized RSN
// 2. Read each "skills/all" category snapshot by index
// 3. Read relevant snapshotStates by player/category
// 4. Run pure null-aware comparison
// 5. Return one bounded read model
Specific collection item comparison
comparisons.getItem({
  leftRsn: "player a",
  rightRsn: "player b",
  category: "collection",
  canonicalKey: "item.twisted_bow"
})

// Resolve players and active collection revisions,
// then perform two indexed canonicalItems lookups.
// Return each player's possession and quantity.

Public Convex API

  • players.getSummary({ rsn })
  • comparisons.getCategory({ leftRsn, rightRsn, category })
  • catalog.search({ category, query })
  • comparisons.getItem({ leftRsn, rightRsn, category, canonicalKey })
  • providerHistory.get({ rsn, provider, metric, range }) // action
  • freshness.getForComparison({ leftRsn, rightRsn })
  • refresh.request({ rsns })

Read model guarantees

  • Every current metric identifies its authoritative source and fetch time.
  • Every category includes completeness and slice freshness.
  • Missing values remain null and comparisons become indeterminate.
  • Queries return only the route's category, keeping subscriptions bounded.
  • Provider history is transformed on demand but never persisted.
08

Freshness, retries, and operations

MISSING

No successful canonical snapshot yet.

SCHEDULED

Lease acquired and action queued.

REFRESHING

External fetch currently running.

FRESH / STALE

Usable current snapshot with visible age.

UNAVAILABLE

Not found, not connected, private, rate-limited, or failed.

Hourly refresh gate

refresh.request checks the database-configured cooldown and the player's refreshAllowedAt. The initial policy permits at most one successful snapshot refresh per normalized RSN per hour.

Stale-write protection

Every batch carries a request ID. The commit mutation ignores a run that no longer owns the player's refresh lease, preventing an older action from replacing a newer current snapshot.

Replace, never append

A successful granular refresh writes a new revision, atomically makes it active, then cleans up the old revision in bounded batches. Failed refreshes leave the prior revision active.

Operational signals

Track success rate and latency by source/category, 429 frequency, cooldown rejections, source contract failures, stale snapshots, replacement failures, and documents approaching size limits.

PHASE 1

Build one complete vertical slice

Hiscores → canonical skills and activity snapshots → two-player comparison query. Include the hourly refresh gate, player lease, replacement writes, fixtures, and null-aware comparison.

PHASE 2

Complete Hiscores coverage

Normalize every official hiscores skill and activity into canonical keys. Add bossing, clues, minigames, and contract-drift tests before integrating another provider.

PHASE 3

Add segmented rich data

Add RuneProfile quests, diaries, combat tasks, and collection pages as current canonicalItems rows. Build item search and two-player item lookup.

PHASE 4

Harden and operate

Add WOM current efficiency data and provider-history passthrough actions. Add optional API-key configuration, normalization fixtures, cooldown controls, and source health dashboards.

Confirmed implementation constraints

  1. 1. Current normalized RSN is the only RuneRating player identity.
  2. 2. Persist only current canonical snapshots; keep no raw payloads or RuneRating history.
  3. 3. Hiscores owns every overlapping canonical metric.
  4. 4. Initial refresh cooldown is configurable and targeted at one hour per player.
  5. 5. Rich provider data must support granular, searchable item/task comparisons.
  6. 6. Implement all official Hiscores data before adding other providers; assume no API keys initially.
